# CAID roadmap

This roadmap starts from v0.31.0. It describes the currently known work needed to turn CAID from a useful KiCad 10 prototype into a dependable, general-purpose circuit and PCB design assistant. The Amiga ROM adapter is one demanding test project, not a product-specific mode or the basis for general electrical assumptions.

## Planning basis

- Estimates are **engineering effort for one full-time developer**, including implementation, automated tests, Windows/KiCad integration checks, and documentation. They are ranges, not release dates. Hardware research, physical measurements, board fabrication, and feedback cycles are additional time.
- Each milestone produces a usable improvement. Work can overlap, but the dependency order below should guide releases. Reassess estimates after the first real projects in each category.
- `CAID-Projekt.json` holds requirements, decisions, sources, and unresolved questions. Saved KiCad schematics and boards hold the actual circuit and geometry. A model proposal becomes a design change only after deterministic validation and a reviewable preview.
- CAID targets KiCad 10 on Windows now. KiCad 10's IPC plugins run in the PCB Editor. **All planned schematic creation and editing in M2–M3 uses saved `.kicad_sch` files**: stage an isolated project copy, edit the file, validate it with `kicad-cli`, preview the diff and PCB impact, then apply the reviewed revision. There is no KiCad 11 dependency for these features. KiCad 11 editor integration is a later optional compatibility project. [KiCad IPC add-on documentation](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/)

## Current baseline

M1 and M2 are in progress. v0.23.8 adds a bounded subprocess for the KiCad context probe, process-tree cancellation, another source check before publishing a design or route copy, unique schematic backups, and a repeatable Windows KiCad integration script. v0.23.9 also fingerprints the schematic, project rules, project brief, and local libraries during routing and rejects copies based on changed inputs. v0.24.0 marks in-progress project copies with file locks and provides recovery commands for abandoned jobs. v0.24.1 reports saved PCB file presence, refreshes the KiCad client after each successful probe, and discards pending changes when the connection is lost. v0.24.2 validates placement previews against the full live PCB serialization and ignores model-context metadata during that check. v0.25.0 adds a provider-independent operation to rename local net labels on a single sheet, verified against the complete KiCad netlist and ERC before review. v0.26.0 adds a bounded operation to connect an unconnected pin to an existing local net, with an exact netlist delta and ERC gate. v0.27.0 moves the PCM wxPython requirement to 4.3; the user confirmed the updated chat opens in KiCad 10. v0.28.0 adds reviewed no-connect markers for explicitly unused pins, checked against KiCad netlist and ERC. v0.29.0 can disconnect a pin attached through an exact local label, with an exact netlist check and prominent review of new ERC errors. v0.30.0 lists newly introduced KiCad ERC findings, affected items, and positions in every reviewed schematic proposal. Editor restart and upgrade scenarios still need broader in-editor coverage. M2 still needs structured symbol creation, wire-based pin changes, and power-marker operations.

CAID already installs through a KiCad PCM repository; connects to the open PCB; reads saved schematic netlists; runs ERC and DRC; tracks a project brief; stages new single-sheet circuits and unrouted boards; previews selected schematic fields and PCB placement; and routes bounded batches on isolated PCB copies. It supports WSL CLIs, cloud APIs, and local model servers. Routing uses local path search followed by KiCad DRC; part evidence is recorded but not independently authenticated. A successful check is evidence for the stated check only.

v0.31.0 additionally supports creating a new local net between two explicitly selected free pins with matching labels, exact KiCad netlist comparison, and ERC review. Structured symbol creation, drawn-wire edits, and power markers remain open.

Show the active document, saved/unsaved state, current operation, and actionable errors. Part and physical evidence** | Match exact manufacturer ordering codes to symbol pins, package drawings, footprint pads, orientation, body/courtyard height, connector accessibility, and 3D models. M1 and M2 are the next implementation priorities. M2 and M3 are deliverable with KiCad 10 through file-backed edits and CLI validation; they should not wait for KiCad 11. M3 should precede claims that CAID can create general multi-sheet projects. M4 can start in parallel after M1's integration harness exists. M5 should feed M3 and M7 rather than be treated as a late cosmetic check. M6 should be delivered incrementally throughout M1–M5 even though its final acceptance is listed separately.

## Cross-cutting requirements

- **Safety of edits:** stage work in copies; hash source files; detect concurrent changes; show a diff and KiCad check results; retain a recoverable backup; apply only the reviewed revision.
- **Electrical truth:** compare proposed pin/net assignments to KiCad's exported netlist. Use ERC, DRC, and schematic/PCB parity as separate gates. Add domain-specific checks only when the necessary limits and sources are known.
- **Physical truth:** compare installed footprints and supplied package evidence; measure actual geometry in the saved PCB; track the reference surface for height and clearance. A 3D model or datasheet URL is evidence to inspect, not proof of fit.
- **Reproducibility:** every generated design and routing pass records inputs, tool versions, source hashes, constraints, outputs, skipped work, and open questions. Keep test projects separate from the product's general logic.
- **Provider behavior:** cloud, WSL, and local models may differ in output quality, but validation and available structured operations should not depend on the vendor. Give clear errors for unsupported models or malformed proposals.
- **Language and accessibility:** follow KiCad's language setting with English fallback, keep keyboard operation usable, and make long conversations and previews readable in a narrow window.

## Validation projects

1. **Small generic board:** power input, connector, passives, and a simple IC. Exercises new-circuit generation, placement, 1–2 layer routing, BOM, and export.
2. **Existing populated board:** deliberately stale schematic/PCB, local libraries, zones, keepouts, and partial copper. Exercises review, synchronization, incremental edits, and route continuation.
3. **Multi-sheet board:** repeated units, inherited symbols, buses or hierarchical labels, and custom fields. Exercises general schematic editing and KiCad parity.
4. **Mechanically constrained adapter:** the Amiga ROM replacement variants, including separate 40-pin, 42-pin, and CDTV requirements. Exercises exact socket geometry, voltage translation, dual-image switching, programming access, and top/bottom clearances. No variant inherits another variant's pinout without an explicit, verified mapping.

## Release gates

A milestone is complete only when its documented user path works in an installed KiCad package, the automated suite and relevant Windows KiCad integration fixtures pass, the original project is preserved for rejected proposals, and the report distinguishes verified checks from unresolved claims. Routing additionally requires no new KiCad DRC findings, fewer open connections for each accepted step, and unchanged schematic parity. Hardware fabrication still requires review of the actual parts, target machine, manufacturing rules, and test results.

## Estimate and boundaries

A useful **general-design beta** through M1–M3 is roughly **12–21 developer-weeks**. A broader release through M7 is roughly **31–54 developer-weeks** of sequential effort, plus hardware validation and any advanced-router research. These figures assume full-time work and stable KiCad/provider interfaces. They do not promise complete automatic routing, automatic proof of electrical function, or fabrication readiness from ERC/DRC alone.

Not planned as a shortcut: embedding Freerouting, silently editing the live board, treating unsourced pinouts as facts, or promising a docked sidebar in KiCad 10. KiCad 10's documented plugin scope is the PCB Editor; future editor support must be assessed against the actual released KiCad API. [KiCad IPC documentation](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/) KiCad design rules and DRC remain part of the acceptance checks, including project-specific `.kicad_dru` rules. [KiCad 10 PCB Editor documentation](https://docs.kicad.org/10.0/en/pcbnew/pcbnew.html)
